# MCP Connection

This section describes `fn mcp serve` — the Fusion **operator MCP server**, the
inverse of the pi-extension surface documented above. Where the rest of this
skill is loaded by Fusion's own agents (triage/executor/reviewer/merger), this
section is for an *external* MCP client (Claude Desktop, Claude Code, or any
other MCP-speaking tool) that connects to a running Fusion project directly.

## Transport model

`fn mcp serve` exposes two transports:

- **stdio** (default) — a local subprocess launched directly by the operator's
  own MCP client, communicating over stdin/stdout using newline-delimited
  JSON-RPC 2.0. This is the trust boundary: every call is treated as an
  already-authenticated operator action running with the operator's own OS
  privileges. There is no additional network-facing auth check on this
  transport.
- **streamable-HTTP** — an opt-in transport (`fn mcp serve --transport http`)
  that binds a real HTTP listener. Non-loopback binds require a bearer token;
  loopback binds without a token are allowed but emit a startup warning. Use
  this when the MCP client cannot spawn a local subprocess (e.g. a remote
  client, or a client that only speaks HTTP).

Both transports serve the exact same tool registry and the exact same
`fusion://skill` resource this document is part of — the resource is
guaranteed fetchable over either transport (see the automated coverage that
proves this).

## Curated tool surface

The MCP curated surface is a **subset** of the full pi-extension `fn_*` tool
surface documented in the rest of this skill (`extension-tools.md`) — the pi
extension exposes the complete first-party tool catalog to Fusion's own
agents, while `fn mcp serve` exposes only the operator-safe subset an
external MCP client should be able to drive directly. The base tier is
read + safe-mutation only; the destructive tier (delete/hard-mutation tools)
is off by default and only appears when the operator explicitly launches
`fn mcp serve --allow-destructive`.

The list below is generated from the SAME `buildMcpToolRegistry` function
`fn mcp serve` calls to build its live registry (see
`packages/cli/src/mcp-server/tools.ts`) — it cannot silently drift from what
the server actually registers. Tools annotated `--allow-destructive`-gated
are part of the destructive tier: they are always documented here (the served
skill content never varies with the runtime flag), but are only registered
on the live server when the operator passes `--allow-destructive`.

## Tool-invocation conventions

- Every MCP tool name matches its pi-extension `fn_*` counterpart 1:1 (same
  name, same argument shape) — there is no separate MCP-only naming
  convention to learn.
- Arguments are validated against each tool's declared JSON-Schema
  `inputSchema` before dispatch; required fields are enforced by the
  transport's own schema validation, not by the handler.
- Every tool call dispatches to the SAME `@fusion/core` / `@fusion/engine`
  domain operation the pi-extension handler for that tool name calls — no
  duplicated validation, no HTTP dashboard round-trip.
- Tool results are plain `text` content blocks; secret-bearing fields (e.g.
  settings values) are redacted before serialization.
- Destructive-tier tools are gated behind `fn mcp serve --allow-destructive`
  and are never registered on a server started without that flag, regardless
  of what this document advertises.
