summary: Proactively pause before hitting the Claude usage limit, reserving headroom, with usage-bar warnings and notifications.
category: feature
dev: Adds a proactive `globalPauseReason: "usage-threshold"` trigger — `SelfHealingManager.checkUsageThresholdPause` (maintenance batch 1, paused-safe) reads `settings.usagePauseThresholdPercent` plus the FUSI-057 `getUsageControlSnapshot()` DI callback each tick and, when worst-case Claude usage (5h or weekly window) crosses the configured threshold and no pause is already active (any reason, including `"manual"`), calls the new `UsageLimitPauser.onUsageThresholdReached(...)` entry point (`packages/engine/src/usage-limit-detector.ts`). A subsequent hard rate-limit hit escalates an active `"usage-threshold"` pause to `"rate-limit"` in place. The FUSI-053 reset-aware auto-unpause resumes a `"usage-threshold"` pause using the snapshot's `soonestResetAt`/`soonestResetMs` (falling back to blind backoff), so it never sits paused forever; `autoUnpauseEnabled`/`"manual"` semantics are unchanged and the hard `"rate-limit"` path is unaffected. Fires opt-in `usage-threshold-pause`/`usage-threshold-resume` ntfy events (new `NtfyNotificationEvent` values, NOT in `DEFAULT_GLOBAL_SETTINGS.ntfyEvents` by default) with a 15-minute dedupe cooldown. `UsageIndicator.tsx` renders an inline threshold marker plus a near-limit warning banner (10-percentage-point approach band, `--color-warning`/`--color-error`) on the Claude usage-bar rows across modal/embedded presentations and mobile breakpoints, sourced from the existing `useAppSettings` hook (no second settings fetch). Settings → Scheduling exposes `usagePauseThresholdPercent` and `usageThrottleThresholdPercent` (FUSI-059) as blank-is-off number inputs; NotificationsSection lists the two new opt-in ntfy events. Feature is fully off (no pause, no notification, no marker/warning) when `usagePauseThresholdPercent` is undefined.
