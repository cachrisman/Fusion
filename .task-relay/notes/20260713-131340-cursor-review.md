## Code review: `agent-tools.ts` (+ related diff)

### High
- None identified.

### Medium
- **`kind: 'fragment'` suppresses lifecycle warnings without validating fragment shape.** The new parameter is passed straight to `store.createWorkflowDefinition`, and the store only checks `input.kind === "fragment"` — it does not enforce the “single-node template” contract described in the schema. `analyzeWorkflowLifecycle` returns `[]` for any fragment regardless of IR complexity (`packages/core/src/workflow-lifecycle-validation.ts:92`). An agent can mark a full, unsafe workflow as `fragment` and get zero `lifecycleWarnings` in the response. Hard merge guards still apply at runtime, but this diff newly exposes that bypass on the agent/MCP create path (the dashboard `POST /api/workflows` route still does not accept `kind`).

### Low
- **`fn_workflow_create` prose does not mention `kind`.** The long `description` string (lines ~2588–2613) documents IR constructs but not the new `kind` parameter. Agents that lean on tool descriptions over JSON Schema may never learn they can create fragments or what that implies.
- **`lifecycleWarnings` are only in `details`, not in human-readable `content`.** Success text is still `Created workflow …` / `Updated workflow …` with no mention of warnings. Pi agents that only read `content[0].text` will miss guidance; MCP clients reading `structuredContent` will see it — asymmetric surfacing.
- **Read/write asymmetry for `kind` and warnings.** Create/update now return `kind` + `lifecycleWarnings` in `details`, but `fn_workflow_get` still omits both from `content` and `details` (pre-existing). MCP clone flows (`get` → `update`) cannot recover `kind` or warnings from the read step.
- **`fn_workflow_update` cannot set or change `kind`.** Create accepts `kind`, but `workflowUpdateParams` has no `kind` field and the update call does not pass one. Agents can create fragments but cannot convert workflow ↔ fragment later (matches `WorkflowDefinitionUpdate`, but the API is asymmetric).
- **No test updates for the new behavior.** `agent-tools.test.ts` still mocks `{ id, name }` without `kind`/`lifecycleWarnings`; nothing asserts `kind` passthrough or warning surfacing.

### Informational / non-issues
- **Store integration looks correct.** `kind: params.kind` matches `WorkflowDefinitionInput`; omitted/`undefined` correctly defaults to `"workflow"` in the store (`store.ts:15813`). TypeBox `Union` literals reject invalid values at the tool boundary.
- **`lifecycleWarnings` on update are fresh.** The store recomputes them on every update using `existing.kind` (`store.ts:16063`); returning them in `details` is accurate.
- **`reviewer.test.ts` mock additions look correct.** Stubbing `wrapToolsWithRtkRewrite`, `wrapToolsWithPermanentAgentGating`, and `wrapToolsWithActionGate` as pass-through functions matches the production `createResolvedAgentSession` tool chain and fixes a real test-runtime gap. No functional concern there.

### Security
- No new privilege escalation or auth bypass. Workflow authoring tools already run with operator-level trust; exposing `kind` does not let agents assign fragments to tasks (`selectTaskWorkflow` rejects fragments) or set them as project defaults. The main risk is **correctness/policy guidance loss** (mislabeled fragments, hidden lifecycle warnings), not a security boundary break.
